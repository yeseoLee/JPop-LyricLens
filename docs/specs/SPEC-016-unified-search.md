# SPEC-016 통합 곡 검색 (제목·아티스트·가사·의미·별명·줄임말·오탈자)

- 상태: 진행 중
- 이슈: #33
- 구분: 확장 (X-07, D-13)
- 대응 요구사항: 해당 없음 (F2011 조건 탐색·F2010-b 구절 검색과 함께 쓰는 검색창)
- 관련 절: `docs/specs/SPEC-015-benchmark.md`, `docs/benchmark.md`

## 1. 목적
검색창 하나로 곡을 찾는다. 질의는 제목(원제·번역·로마자), 아티스트(별명·줄임말 포함), 가사 한 줄(ko/en/ja), 설명(의미·타이업) 중 무엇이든 될 수 있고, 오탈자가 있어도 된다.

기준선(SPEC-015)에서는 단일 시스템 중 최고가 `meta_vector` MRR@10 0.624였다. 범주마다 잘하는 시스템이 달랐다. 가사는 `lyrics_vector`, 제목·아티스트는 `meta_vector` 가 강했고, 별명·줄임말·의미 범주는 모든 시스템이 약했다.

## 2. 설계 — 여러 채널을 순위 결합(RRF)

### 2.1 정규화 `normalize_query(text)`
NFKC → 소문자 → 공백·문장부호 제거 → 가타카나를 히라가나로 → 장음 `ー` 제거.

### 2.2 채널
| 채널 | 방식 | 잘 잡는 범주 |
|------|------|--------------|
| `lexical` | 곡 카탈로그(§2.3)의 모든 이름과 질의를 정규화해 비교한다. 완전 일치 1.0, 포함 0.9, 그 밖에는 문자 bigram Dice와 `difflib` 비율 중 큰 값. 0.75 이상만 후보로 둔다. 아티스트 이름이 맞으면 그 아티스트의 곡 전부, 제목이 맞으면 그 곡. 질의에 아티스트와 제목이 함께 있으면(혼합) 둘 다 맞는 곡을 맨 앞에 둔다 | 제목·아티스트·별명·줄임말·로마자·오탈자·혼합 |
| `meta_vector` | `song_meta` 의미 유사도 (원 질의 + LLM 재작성 질의) | 의미·타이업·설명 |
| `lyrics_vector` | `song_lyrics` 유사도, 곡별 최고 점수 (원 질의 + 일본어 재작성) | 가사 |
| `llm_guess` | 보조 모델 1회 호출로 질의를 해석한다: `{"kind": title\|artist\|lyrics\|description, "ja_query": 일본어 검색어, "title_guess": [...], "artist_guess": [...]}`. 추정한 제목·아티스트는 `lexical` 로 카탈로그에 맞춘다 (카탈로그에 없는 곡은 버림) | 의미·타이업·번역 제목 |

### 2.3 곡 카탈로그 (`config/`, 커밋)
- `config/artist_aliases.yaml`: 아티스트 40명 전체의 로마자·한국어 변형·널리 쓰이는 줄임말·애칭. 40명을 같은 기준으로 적고, 벤치마크 test 케이스에 맞춰 특정 항목만 넣지 않는다.
- `config/title_aliases.yaml`: 곡 240개 전체의 한국어 제목(번역·음역)·영어 제목·로마자. `scripts/build_title_aliases.py` 가 주 모델로 한 번 만들고 사람이 검토할 수 있게 커밋한다. 있으면 다시 만들지 않는다.
- 제목 읽기(`title_kana`)의 히라가나를 헵번식 로마자로 바꾼 표기도 자동으로 넣는다 (`kana_to_romaji`).

### 2.4 결합
- 채널별 순위로 가중 RRF를 계산한다: `score = Σ w_c / (k + rank_c)`, `k = 60`.
- 가중치(`search.weights`)는 `lexical 1.0`, `llm_guess 0.8`, `meta_vector 0.6`, `lyrics_vector 0.6` 으로 시작하고, dev split 만 보고 조정한다.
- `lexical` 완전 일치(1.0)는 결합 점수와 관계없이 맨 앞에 둔다.
- 상위 `search.top_k`(10)곡을 돌려준다. 곡마다 걸린 채널과 이유(예: `별명 일치: 히게단 → Official髭男dism`)를 함께 준다.

### 2.5 비용
- 질의당 보조 모델 1회(~1초)와 임베딩 2회.
- `search.use_llm: false` 면 `llm_guess` 를 끄고 나머지 채널만 쓴다. 이 경우도 벤치마크에서 따로 잰다.

### 2.6 화면
- 사이드바 맨 위에 "곡 검색" 입력창을 둔다.
- 결과 목록에서 곡을 고르면 선택 곡이 바뀐다.
- 결과마다 매칭 이유를 짧게 보여 준다.

## 3. 평가
- `bench_run.py search` 에 `unified`, `unified_nollm` 시스템을 추가한다.
- dev·test 를 따로 보고한다. 가중치·사전은 dev 만 보고 조정한다.
- 목표: 전체 MRR@10 0.80 이상(test). 범주별로 기준선보다 낮아지는 범주는 원인을 기록한다.
- 한계: 벤치마크 케이스와 사전을 같은 작성자(에이전트)가 만들었다. 그래서 별명·줄임말 범주는 누수 가능성이 있고, 보고서에 그대로 밝힌다.
