# RAG 파이프라인 설계문서

JPop LyricLens의 수집·색인·검색·생성 흐름과, 그렇게 정한 이유를 정리한다. 요구사항 번호는 PRD 기준이다. 세부 동작은 `docs/specs/SPEC-00x-*.md` 에 있다.

## 1. 전체 흐름

```
[사전 준비]  UtaTen ──수집──▶ data/songs.jsonl ──항목 텍스트──▶ Chroma: song_meta
                                             └──가사 연 분할──▶ Chroma: song_lyrics

[질문 시]    질문 + 선택 곡
              │ 프롬프트 1: 검색어 추출 (+ 곡 제목·아티스트 기본 검색어)
              ▼
            ko.wikipedia 검색 ─▶ 1차 문서(곡·아티스트) 항상 수집
              │ 프롬프트 2: 후보 선별 → 고른 문서만 본문 수집
              ▼
            청킹(1000/200) ─▶ Chroma: wiki_docs        (수집 캐시: 같은 곡·검색어는 다시 안 함)

            LangGraph:  START → retrieve → generate → END
              retrieve: song_meta(ID 조회, 항상 1번) + song_lyrics·wiki_docs(곡 범위 유사도 검색)
                        → 병합 → 중복 제거 → [근거 1..N]
              generate: 프롬프트 3 → 답변 → 인용된 [근거 N]만 화면에 표시
```

모듈 배치(NF2005): 도메인(UtaTen·J-POP)에 묶인 코드는 `src/lyriclens/domain/` 에만 있고, `collect/`(수집)·`index/`(Vector Store)·`rag/`(검색·생성)·`services/`(특화 기능·탐색)·`ui/`(화면)은 도메인 파일을 모른다. 이 규칙은 `tests/test_architecture.py` 가 검사한다.

## 2. Vector DB 컬렉션 (F2002, F2005)

| 컬렉션 | 단위 | 청크 ID | 메타데이터 |
|--------|------|---------|-----------|
| `song_meta` | 곡 1개 = 1청크 | `{song_id}` | song_id, title, artist, artist_ko, lyricist, composer, release_date, release_year(int), tieup, url, source_type=`song_meta` |
| `song_lyrics` | 가사 연(빈 줄 기준, 최대 8줄) | `{song_id}:L{n}` | song_id, title, artist, stanza_seq, url, source_type=`lyrics` |
| `wiki_docs` | 위키 문서 청크 | `{song_id}:{page_id}:{n}` | song_id, song_title, doc_title, doc_id, url, query, is_primary, collected_at, source_type=`wikipedia` |

- **곡 정보를 따로 둔 이유**: 선택한 곡의 기본 사실(크레딧·발매일·타이업)은 질문과 상관없이 늘 필요하다. 그래서 검색하지 않고 ID로 꺼내 항상 1번 근거로 넣는다.
- **가사 연 컬렉션을 따로 둔 이유**: 곡 전체 텍스트 한 덩어리로는 "이 구절이 나오는 곡" 같은 구절 단위 검색이 흐려진다. 연 단위로 나누면 구절 검색(F2010-b)과 해석 근거(F2010-a)를 정확히 짚을 수 있다.
- **`song_id` 필터**: `wiki_docs`·`song_lyrics` 검색은 늘 `where={"song_id": 선택 곡}` 으로 좁힌다. 이 필드가 빠지면 다른 곡의 문서가 근거에 섞인다.
- **청크 ID에 곡 ID를 넣은 이유**: 같은 위키 문서(예: 아티스트 문서)를 여러 곡이 수집해도 서로 덮어쓰지 않게 하려는 것이다. 곡 정보는 ID가 곡 ID 하나라서 다시 색인해도 덮어쓰기만 일어난다.
- 거리 함수는 cosine.

## 3. 항목 텍스트 (F2001)

```
제목: Lemon (れもん)
아티스트: 米津玄師 / 요네즈 켄시
작사: 米津玄師 / 작곡: 米津玄師
발매일: 2018-03-14
타이업: ドラマ 「アンナチュラル」 主題歌
가사:
(가사 원문)
```

사용자가 곡을 찾는 기준을 모두 넣었다. 아티스트의 한국어 표기가 있어 한국어 질의로도 걸리고, 타이업이 있어 "애니 주제가" 같은 조건이 걸리며, 가사가 있어 "이별 노래" 같은 내용 조건이 걸린다. 값이 없는 줄은 빼고, 6,000자를 넘으면 가사 끝을 자른다.

## 4. 문서 수집·청킹·색인 (F2003~F2005)

1. **검색어**: 곡 제목·아티스트(한국어 표기 우선)는 LLM 결과와 상관없이 맨 앞에 넣는다. 그 뒤에 프롬프트 1의 검색어를 최대 4개 붙인다.
2. **캐시 확인**: 이미 수집한 `(song_id, 검색어)` 는 건너뛴다 (`data/cache/collected.json`, NF2002).
3. **1차 문서**: 곡 문서와 아티스트 문서를 찾는다. 곡 문서가 없으면 아티스트 문서가 그 역할을 한다. 1차 문서는 선별이나 길이 기준과 상관없이 항상 수집한다.
4. **후보 선별**: 나머지 검색어로 검색어당 후보 5개를 모은다. 제목·요약만 프롬프트 2에 보여 주고, 고른 문서만 본문을 받는다. 본문을 받기 전에 버릴 문서를 정하므로 외부 호출 수가 줄어든다.
5. **청킹**: `RecursiveCharacterTextSplitter(chunk_size=1000, chunk_overlap=200)`, 구분자 `\n\n → \n → 。 → . → 공백` (한국어·일본어 문장 경계 고려).
6. **색인**: `wiki_docs` 에 upsert한다.

외부 호출 예절(NF2006)은 `src/lyriclens/http.py` 공통 규칙을 따른다. 호출 간격(위키 1초, UtaTen 3초), 429·5xx·연결 오류 지수 백오프 최대 3회, 연락처가 든 User-Agent가 포함된다.

## 5. 검색 결과 병합과 중복 제거 (F2006)

1. `song_meta` 에서 선택 곡을 ID로 조회해 1번에 둔다.
2. `song_lyrics` 에서 질문과 비슷한 연 3개(`lyrics_top_k`)를 가져온다.
3. `wiki_docs` 에서 질문과 비슷한 청크 5개(`wiki_top_k`)를 가져온다.
4. 메타 → 가사 → 위키 순서로 합친다. 같은 청크 ID, 그리고 **출처 유형과 본문이 같은** 청크는 처음 것만 남긴다. 서로 다른 문서에 같은 문단이 있어도 근거는 하나로 센다.
5. 1부터 다시 번호를 매기고 출처 유형 라벨(곡 정보 / 가사 / 위키백과)을 붙인다.

## 6. 프롬프트 (`src/lyriclens/rag/prompts.py`)

| 프롬프트 | 역할 | 입력 | 출력 형식 | 실패 시 |
|----------|------|------|-----------|---------|
| **프롬프트 1** 검색어 추출 | J-POP 평론가·일본 대중문화 전문가 | 곡 제목·아티스트·타이업·질문 | JSON 문자열 배열 (최대 4개) | 1회 재요청 → 기본 검색어만 |
| **프롬프트 2** 후보 선별 | J-POP 자료 조사원 | 후보의 page_id·제목·요약, 질문 | JSON 정수 배열 (page_id) | 1회 재요청 → 1차 문서만 |
| **프롬프트 3** 답변 생성 | J-POP 가사·배경 해설가 | 최근 대화 4개, `[근거 N] (유형) 제목` 블록, 질문 | 자유 서술 + `[근거 N]` | 근거 0개면 호출하지 않고 "확인되지 않습니다" |

프롬프트 3의 규칙은 다음과 같다.
- 근거에 있는 내용만 쓴다.
- 확인되지 않으면 "제공된 문서에서 확인되지 않습니다"라고 쓴다.
- 주장마다 `[근거 N]` 을 붙인다.
- 가사 원문은 한 번에 최대 4줄까지 인용하고, 전문을 옮겨 적지 않는다.
- **답변 언어**: 코드가 질문 언어를 판별해 `답변 언어: English` 처럼 명시한다. "질문과 같은 언어로" 라는 규칙만 두었을 때는 실제 실행에서 영어 질문에 한국어로 답했다. 시스템 프롬프트와 근거가 대부분 한국어였기 때문이다(#26).

그 밖에 특화 기능·탐색용 프롬프트가 있다. 조건 해석(JSON 객체), 조건 선별(JSON 배열 + 이유), 구절 해석(JSON 객체: 번역·풀이·배경), 일본어 가사 표현 변환(JSON 배열)이다. 모든 JSON 응답은 코드블록·앞뒤 설명문을 허용하는 파서(`jsonparse.py`)로 읽고, 실패하면 1회 다시 요청한다.

## 7. 청크 크기·중복·Top-k를 정한 이유와 바꿨을 때

| 설정 | 값 | 이유 | 바꿨을 때 (실측, 2026-10-21) |
|------|-----|------|------|
| `chunk_size` / `chunk_overlap` | 1000 / 200 | 위키 문서 한 절(배경·타이업·평가) 정도가 한 청크에 들어가는 크기다. 중복 200자를 두어 절 경계에서 문장이 잘려도 앞뒤 맥락이 남는다 | 「夜に駆ける」 수집 문서 2개: 1000/200 → 4청크, 500/100 → 9청크. 작게 자르면 근거 하나에 담기는 맥락이 줄어 같은 문서가 근거 목록을 여러 칸 차지한다 |
| `wiki_top_k` | 5 | 곡 정보 1 + 가사 3과 합쳐 근거 9개 안팎이다. nano급 모델도 번호를 헷갈리지 않는 길이다 | 3 → 6: 같은 질문의 근거가 7개 → 8개(이 곡은 위키 청크가 적어 1개만 늘어남). 문서가 많은 곡에서는 아티스트 일반 문서가 끼어들기 시작한다 |
| `lyrics_top_k` | 3 | 질문과 관련된 연만 넣는다. 가사 전체를 넣으면 근거가 가사로 채워지고 저작권 노출도 커진다 | — |
| `lyrics_chunk_lines` | 8 | 일반적인 연(4~8줄)이 한 청크에 들어간다 | — |
| `search_type` | similarity | MMR(F2014)은 확장 단계에서 비교한다 | — |

## 8. 근거 표시 (F2008)

- 답변 본문에서 `[근거 N]`, `[Source N]`, `[根拠 N]`, `[근거 1, 3]` 표기를 정규식으로 찾는다. 실제로 있는 번호의 근거만 번호순으로 표시한다.
- 표시 형식은 `[근거 N] 제목 · 유형 · 원문 링크` + 미리보기다. 가사 근거의 미리보기는 4줄까지, 위키는 200자까지다.
- 인용이 하나도 없으면 "답변에 인용된 근거가 없습니다"라고 안내한다.

## 9. 도메인 특화 기능 설계 이유 (F2010)

외국인 J-POP 팬이 가사 사이트에서 가장 많이 하는 일은 두 가지다. 하나는 "이 구절이 무슨 뜻이지?", 다른 하나는 "그 노래 제목이 뭐였지?"다.

- **가사 구절 해석**: 공백을 무시하고 구절이 든 연을 찾는다. 곡 정보 + 그 연 + 곡 범위 위키 청크를 근거로, 번역(한국어/English)·표현 풀이·곡 배경과의 연결을 만든다. 근거에 없는 배경은 쓰지 않는다. 가사에 없는 구절이면 LLM을 부르지 않고 "찾지 못했습니다"라고 답한다.
- **구절로 곡 찾기**: 기억나는 가사를 아무 언어로 입력받는다. 일본어가 아니면 LLM이 원래 일본어 가사였을 법한 표현 1~2개를 만들고, 원문 입력과 함께 `song_lyrics` 를 검색해 곡별 최고 점수로 묶는다. 실측 결과, 한국어 「꿈이라면 얼마나 좋았을까」 입력에서 「Lemon」이 1위였다.

## 10. 겪은 문제와 해결

| 문제 | 원인 | 해결 |
|------|------|------|
| 수집한 240곡 중 발매일이 32곡만 채워짐 | `2025.9.24` 처럼 월·일에 0이 없는 날짜를 정규식이 놓침 | `\d{1,2}` 로 고치고 0을 채워 정규화 (#14). 239/240 |
| 제목에 타이업 문구가 섞임 (`IRIS OUT 劇場版「チェンソーマン レゼ篇」主題歌`) | 제목 요소 안의 부제목 요소를 같이 읽음 | 부제목(`.newLyricTitle__subTitle`)을 타이업으로 분리 (#14). 126곡에 타이업 |
| 검색 Top-k 테스트가 간헐적으로 실패 | 테스트 데이터에 같은 본문 청크가 있어, 상위에 같이 들면 중복 제거로 하나가 빠짐 | 구현은 의도대로 동작. Top-k 테스트는 중복 없는 데이터로 분리 |
| 영어 질문에 한국어로 답함 | "질문과 같은 언어" 규칙이 한국어 프롬프트·근거에 밀림 | 코드가 언어를 판별해 프롬프트에 명시 (#26) |
| 「Lemon」 질문에서 관련 문서 「언내추럴」을 버리고 무관한 「체인소 맨」을 색인 | `gpt-5.4-nano` 의 후보 선별 품질 | `gpt-6-luna` 로 바꾼 뒤 「언내추럴」을 고르고 무관 문서는 버림 (#24) |
| `gpt-6-luna` 가 `temperature=0` 을 거부 | 기본값만 허용하는 모델 | 설정 `temperature: null` 이면 보내지 않음 (#24) |
| 임베딩 모델 교체 후 기존 색인 사용 불가 | 차원 1536 → 3072 | 기존 색인·캐시를 `data/backup/` 으로 옮기고 전체 재색인. README에 안내 |
